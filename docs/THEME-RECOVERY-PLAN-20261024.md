## 每个业务单元的检查方法

每项业务应形成一行可核查记录，字段为：**主题、页面入口、操作、期望写入、实际写入、刷新结果、演出结果、错误/取消行为、证据位置、状态**。优先覆盖正常、空态、错误、取消、重入/刷新五类；权限和离线按该模块适用范围增加。

| 代表场景 | 期望行为 | 容易误判的结果 |
|---|---|---|
| 新档案进入四主题 | 没有真实数据时显示对应空态 | 原 demo 演示名册或账本被当真实数据 |
| 创建任务→首页完成→刷新 | 任务、次数、属性变化一致，完成提示和升级顺序正确 | 只弹成功条，数据库没写；重复奖励 |
| 记一笔→统计→重启 | 流水、账户和统计金额一致，本地离线可用 | 页面临时数组改变就算保存成功 |
| 同伴达到升级阈值 | 同一等级曲线，原主题升级演出消费一次 | 预览链接能播，却真实互动不播；两套宿主重复播 |
| 未登录/无组织/非队长 | 原有空态与真实权限正确 | 为避免空数组报错填一个假的“我”或预览参数冒充权限 |
| AI取消/超时/无配置 | 停止等待、显示真实状态、不额外写结果 | 占位文案冒充真实模型回复 |
| 切换主题→刷新 | 同一份真实数据，正确主题与布局、弹层均可用 | 只看主题颜色变了就报全部通过 |

模块验证以风险为准：针对数据变换和奖励规则使用单元测试，针对数据库/API边界使用隔离集成验证，针对演出和点击链使用浏览器真实路径。文案/说明文件不额外堆镜像测试。完成当前相关检查后不机械反复跑整库。

## 保留、修复与重写的判断规则

| 对象 | 默认处理 | 何时改变决定 |
|---|---|---|
| 四套 demo 的页面、素材、CSS、动画和声音 | 保留为视觉权威，逐项对照 | 发现具体缺失且确定应恢复时，按原包最小恢复；可见变化须符合用户明确授权 |
| 可复用的 store、Dexie 数据与已有 services | 核验后继续用 | 有可复现错误时修；必须迁移数据的变更先准备迁移/回退方案，不能清库重来 |
| 数据适配、事件回调和通知桥 | 优先修接线 | 一个模块的数据/权限与生命周期已严重混杂时，在该模块边界内重写适配，仍保持原渲染 |
| 重复旧页面与历史脚本 | 先标用途、保留 | 确认无引用和不影响回退后，另列清理方案；不能顺手删除 |
| 全项目技术栈 | 保持现状 | 只有核心数据/构建存在可证实的系统性障碍，且局部方案不可行时，重新做迁移评估；目前没有此证据 |

“先修一个闭环”是为了验证接入方式。不能把一个主题通过扩写成四主题通过；也不能因为某个模块麻烦就把全工程判死刑。
